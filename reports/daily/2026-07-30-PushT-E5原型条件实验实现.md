# 2026-07-30 PushT E5 原型条件实验阶段性成果

## 重要进展

- 完成 K=3 trajectory prototype 构造，165 条 train demonstrations 被划分为
  P0/P1/P2 共 57/70/38 条；对应 medoid episodes 为 16/108/140。
- 完成 Mode-BCChunk 与 Mode-Diffusion 正式训练、development 闭环 checkpoint
  selection 和 held-out audit；最终选中 BC step 175000、DP step 125000。
- held-out audit 覆盖 21 条 audit episodes、P0/P1/P2/NULL 和两种模型，共完成
  168/168 条正式闭环 rollout，21/21 首帧环境重建通过。
- Mode-Diffusion 保留了较好的任务完成能力，oracle condition 下成功率为
  12/21（57.1%），高于 Mode-BCChunk 的 7/21（33.3%）。
- 正式评测没有证明语义条件控制：DP 的 P0/P1/P2 adherence 仅为
  14.3%/28.6%/19.0%，BC 为 19.0%/23.8%/19.0%，requested→achieved 混淆矩阵
  均未形成清晰对角线。
- 固定 initial noise 和完整 reverse noise stream 后，切换 condition 仍会改变
  action chunk，说明输入链路有效；主要限制来自 prototype 定义和训练数据缺少同一
  初始状态下的配对、多路线监督。

## 已完成工作

### Prototype 与条件模型

从 E0 完整训练轨迹提取 object-centric 8-token sketch，使用自定义距离和 K-medoids
完成 K=2/3/4 审计，按预注册规则选择最小通过项 K=3。原始 dataset 未被改写，episode
assignment 和 prototype manifest 作为只读 sidecar 保存。

Mode-BCChunk 和 Mode-Diffusion 均在 observation global condition 后拼接同一个
32 维 Prototype/NULL embedding。NULL 使用独立 ID，训练时有 20% condition dropout。
两种模型均从受控随机初始化训练，没有使用外部预训练 checkpoint。

### Checkpoint selection

使用固定的 20 条 development episodes 进行闭环选择。每条 episode 只输入其 GT
demonstration 对应的 oracle prototype；rollout 开始后不读取未来 GT 轨迹。排序依据依次
为闭环成功率、mean max reward 和更早的 training step。

| 模型 | 选中 step | Development success | Mean max reward |
|---|---:|---:|---:|
| Mode-BCChunk | 175000 | 10/20（50.0%） | 0.8506 |
| Mode-Diffusion | 125000 | 14/20（70.0%） | 0.9563 |

该选择只说明相应 checkpoint 在 development 闭环任务上的表现较好，不构成 prototype
可控性的证据。

## 正式评测结果

以下结果属于 `Closed-loop / Formal`。同一 audit episode 下的 P0/P1/P2/NULL 使用相同
环境初态；Mode-Diffusion 还固定了 initial noise 和完整 DDPM reverse noise stream。

### 全任务条件评测

| 模型 | P0 success / adherence | P1 success / adherence | P2 success / adherence | NULL success |
|---|---:|---:|---:|---:|
| Mode-BCChunk | 23.8% / 19.0% | 38.1% / 23.8% | 38.1% / 19.0% | 52.4% |
| Mode-Diffusion | 47.6% / 14.3% | 52.4% / 28.6% | 33.3% / 19.0% | 52.4% |

各 condition 的 BC–DP 配对差异在 21 条样本上均未达到显著水平。raw success 只能反映
模型在该输入下完成 PushT 的能力，不能解释为模型遵守了指定 prototype。

### Oracle 子集与 open-loop

| 模型 | Oracle success | Oracle adherence | Normalized MSE | Denormalized MSE | 闭环 replan p95 |
|---|---:|---:|---:|---:|---:|
| Mode-BCChunk | 7/21（33.3%） | 38.1% | 0.01333 | 804.90 | 10.22 ms |
| Mode-Diffusion | 12/21（57.1%） | 33.3% | 0.01315 | 793.59 | 608.93 ms |

两种模型的 held-out open-loop action error 接近。Mode-Diffusion 在当前样本上的主要优势
是闭环任务成功点估计更高，而不是 prototype adherence 更清晰。

## 结果解释

固定噪声诊断确认，P0/P1/P2/NULL ID 会经过预处理进入模型，并在每次 replan 的所有
reverse steps 中保持有效；不同 ID 的 embedding 权重不同，切换 ID 会改变生成动作。
因此负结果不能归因于 condition 未传入或 DDPM 随机性没有固定。

训练数据的关键限制是：165 个训练初始状态各自只有一条 demonstration 和一个
prototype 标签，没有同一初始状态对应多个成功 prototype 的 paired/counterfactual
supervision。P0/P1/P2 又是完整轨迹事后聚类得到的类别，不是已经验证可从任意初始状态
执行的控制命令。GT dense-trajectory 可视化也显示三组内部离散且跨组重叠。

因此本阶段支持：

- condition 输入链路正确，并且会影响 BC/DP 动作；
- Mode-Diffusion 保留了较好的 PushT 闭环任务能力；
- 当前 prototype、数据和训练组合没有建立可靠的语义模态控制。

本阶段不支持：

- P0/P1/P2 可在任意初始状态下自由切换；
- 各 condition 的 success 差异由模型遵守 prototype 导致；
- NULL 分支已经证明覆盖多个成功且稳定的行为模式；
- Mode-Diffusion 相对普通 Diffusion Policy 存在严格同状态的性能优势。

## 实验字段

- Task suite：PushT
- Dataset size：206 episodes；165 train / 20 development / 21 audit
- Observation keys：96×96 RGB、二维 agent position；历史长度 2
- Action space：二维绝对 target position
- Action horizon：内部 16；闭环执行 `[1:9]` 共 8 步
- Control frequency：10 Hz
- Train loss：选中 checkpoint 附近日志中，BC 为 `0.000`（显示精度舍入），DP 约
  `0.007–0.009`
- Open-loop action error：BC normalized/denormalized MSE 为 0.01333/804.90；
  DP 为 0.01315/793.59
- Closed-loop success rate：oracle 子集 BC 33.3%，DP 57.1%；完整条件结果见上表
- Latency：BC replan p95 10.22 ms；DP DDPM-100 replan p95 608.93 ms
- Failure cases：任务超时、requested/achieved prototype 不一致、轨迹超出全部
  prototype rejection radius，以及少量 sketch 无法提取

## 限制与风险

- selection 和 audit artifact 未绑定唯一源码 commit，正式结果的 code provenance
  仍不完整。
- simulator 初始状态由 dataset 第一帧重建，不是完整 Pymunk snapshot replay。
- 21 条 audit episodes 的统计区间较宽，BC 与 DP 的 condition 差异不能只按点估计排序。
- prototype 分类器会拒识部分有效但落在训练分布半径外的轨迹；adherence 同时受模型和
  prototype 评价器影响。
