## 目标

`target_checkpoint_selection.py` 第 591 行的开环循环是纯串行，全部落在 cuda:0：

```python
for step in sorted(checkpoints):
    offline_error = evaluate_open_loop(checkpoint_path=checkpoints[step], ...)
```

6 个 checkpoint × 2,969 帧 = 17,814 次前向，实测约 4.3 frame/s，合计约 69 分钟，期间另外
七张卡空转。六个 checkpoint 之间完全独立，改成每卡一个 checkpoint 后应降到约 12 分钟。

**唯一的正确性要求：改完之后开环误差必须与改前逐值相同。** 它是选模的第二判据，数值一变
就可能改变已有排名。

## 执行步骤

### 1. 给单 checkpoint 的开环评测加一个 CLI 入口

在 `src/robot_practice/experiments/smolvla_libero/target_checkpoint_selection.py` 里加
`--open-loop-only` 模式，不新建模块：

- 新增参数 `--open-loop-only`、`--checkpoint-step=N`、`--open-loop-output=PATH`，三者同时
  出现时只做一件事：对该 step 的 checkpoint 跑 `evaluate_open_loop`，把结果 JSON 写到
  `--open-loop-output`，然后退出。不读闭环产物、不排名、不发布。
- `--open-loop-only` 与 `--resume` / `--overwrite` 的关系：本模式只写自己那一个 JSON，
  目标文件已存在时按 `--overwrite` 决定覆盖或拒绝。
- 该模式不接受 `--num-gpus`；设备由父进程通过 `CUDA_VISIBLE_DEVICES` 指定，子进程始终用
  它看到的唯一那张卡。

`evaluate_open_loop` 本身**不加 device 参数**，也不改内部任何逻辑——靠
`CUDA_VISIBLE_DEVICES` 隔离，和闭环 job 的做法保持一致
（`b0_checkpoint_selection.py` 第 371–372 行就是 `environment["CUDA_VISIBLE_DEVICES"] = str(gpu)`）。

### 2. 父进程按现有 GPU 池模式分派

把第 591 行那个串行循环换成与闭环同一套调度，照
`b0_checkpoint_selection.py::run_evaluation_jobs`（第 638 行起）的结构写：

- `queue.Queue` 装 `range(num_gpus)` 作 GPU 池；
- `ThreadPoolExecutor(max_workers=num_gpus)`，每个任务从池里取一张卡、起一个
  `subprocess.Popen`（命令即步骤 1 的 `--open-loop-only`）、跑完把卡还回池；
- 任一子进程非零退出立即终止其余子进程并抛错，指出对应日志；
- 每个 checkpoint 一个日志文件，首行写完整命令，落在
  `<output_dir>/logs/open_loop_checkpoint_<step:06d>.log`；
- 结果 JSON 落在 `<output_dir>/jobs/open_loop/checkpoint_<step:06d>.json`；
- 父进程按 step 顺序收集，喂给 `summarize_target_checkpoint`，**排名逻辑一行不动**。

`--num-gpus` 沿用现有参数，不新增。可见 GPU 少于 checkpoint 数时自然退化为分批复用，
不报错。

### 3. `--resume` 复用已完成的开环结果

`--resume` 时，若某个 step 的结果 JSON 已存在且记录的 `checkpoint_id`（或权重 sha256）、
`split_sha256`、`max_frames_per_task` 与本次请求一致，则直接读取、不重跑。任一不一致就重跑。
判定逻辑参照 `_completed_job_metrics`（第 288 行）。

### 4. 进度显示

现在每个 checkpoint 顺序打印 `open-loop task N`，并行后会交错。改为父进程一个总进度条，
单位是 frame，总量 `checkpoint 数 × 2,969`（缩减模式下按实际帧数）。子进程自身的逐任务
进度写进各自日志，不打到父进程 stdout。

- `--open-loop-only` 只写指定 JSON，不写 `checkpoint_results.json` / `selected_checkpoint.json`
  / 不发布 `checkpoints/selected`；
- 父进程构造的子命令包含 `--open-loop-only`、正确的 `--checkpoint-step`，且**不含**

  --run-dir=<smoke run> --num-gpus=6 \

  --output-dir=<out>/par --selected-dir=<out>/par_selected --overwrite

## 判断标准

**执行前写死。**

| 判据 | 阈值 | 不满足时怎么办 |
| --- | --- | --- |
| 数值一致性 | 6 卡并行与 1 卡串行的每个 checkpoint `macro_normalized_mse`、`macro_denormalized_mse` **逐值完全相同** | **停止并回滚**。第二判据数值一变，已有排名就不可信 |
| 排名一致性 | 两次的 `ranking` 顺序与 `ranking_audit` 逐项相同 | 同上 |
| 并行度生效 | 开环阶段有 `min(num_gpus, checkpoint 数)` 张卡同时有负载 | 修实现 |
| 并发上限 | `num_gpus=3` 且 6 个 checkpoint 时，同时运行的子进程 ≤ 3 | 修实现 |
| 加速比 | 6 卡相对 1 卡的开环墙钟时间加速 ≥ 4× | 低于 4× 时先查是否被数据加载或 CPU 预处理卡住，不要盲目加卡 |
| 失败传播 | 任一子进程失败则其余被终止，错误信息指出对应日志 | 修实现 |
| `--resume` | 协议一致时复用、不一致时重跑 | 修实现 |
| `--open-loop-only` 隔离性 | 只写自己那份 JSON，不产出排名/发布物 | 修实现 |
| 单测与 ruff | 全绿 | 修完再往下 |

`evaluate_open_loop` 的抽帧顺序、`_flow_noise_seed` 的派生方式、误差公式、
`checkpoint_rank_key` 都不得改动。任何一处改动都会使「与改前逐值相同」这条判据失去意义。

## 不在本计划范围

- **成批前向。** 现在 batch 恒为 1，成批能再快几倍，但 flow-noise seed 是按
  `(task, episode, frame)` 逐帧派生的，成批时必须保证每帧仍拿到自己那份噪声。这会碰噪声
  生成路径，风险等级和本计划不同，另起计划并配「改前改后逐值相同」的回归测试。
- 闭环部分的调度。它已经是多卡的，不动。
- B0 选模。它没有开环成分。
- 改变判据顺序或开环误差的定义。

## 风险与停止条件

- **数值一旦变化就停。** 开环误差是选模第二判据，它决定闭环打平时谁胜出。本计划只改调度，
  没有任何理由让数值改变；一旦不一致，说明并行引入了状态泄漏或设备差异，回滚而不是调容差。
- **不同型号的卡可能给出不同结果。** 验收必须在同一台机器、同型号卡之间比对。如果生产环境
  混用不同型号 GPU，需要额外记录每个 checkpoint 实际用的卡型，并在报告里说明数值不可跨机比对。
- 六个子进程各自加载一份 SmolVLA（权重约 1.2 GB），显存与主机内存占用是原来的六倍。单卡显存
  不足时降低 `--num-gpus`，不要改 batch。
- 子进程的 stdout 不再直接可见，排查必须看
  `logs/open_loop_checkpoint_<step>.log`。日志首行必须是完整命令。
- 不要顺手把闭环与开环合并成一个统一 job 池。两者的单位（rollout 与 frame）、失败语义和
  复用条件都不同，合并会让 `--resume` 的判定变复杂。
