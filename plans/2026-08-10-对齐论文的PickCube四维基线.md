不按"复现 1.00"设。

### 官方评测没有留出集，这一点必须写明

`evaluate()` 里是 `obs, info = eval_envs.reset()`——**不传 seed**。`make_eval_envs` 只做
`env.action_space.seed(i)` 与 `env.observation_space.seed(i)`，那是给动作/观测空间的采样器播种，
不是给环境的 episode RNG 播种。所以**评测初始状态每轮重新随机抽，不固定、不可复现、也不与演示状态
做隔离**。演示本身录在 seed 0..1003，评测状态与它们同分布且可能重合。

这跟本仓库的纪律相反（PushT 与 LIBERO 都做了固定的留出划分）。处理办法是**两个指标都报**，用途分开：

| 指标 | 协议 | 用途 |
| --- | --- | --- |
| `official_best` | 官方协议，100 局、不传 seed、取训练过程最大值 | **与论文 1.00 / 0.76 直接可比**，是本计划的主指标 |
| `holdout_once` | 固定 seed 的留出集，选中的 checkpoint 只跑一次 | 本仓库口径的无偏数，供我们内部对照与后续阶段引用 |

两者来自同一批训练 run，只多花评测时间（CPU 上几分钟），所以都做。**不要用 `holdout_once` 去和论文
比**，也**不要用 `official_best` 当无偏估计**。

论文那个 1.00 是 max-over-eval-rounds：`eval_freq=5000`、`total_iters=30000` 意味着约 6 轮评测，
每轮 100 局。真实成功率在 0.95 附近时，6 轮里出现一次 1.00 很常见。**所以我们的判据不该要求 1.00。**

## 执行步骤

### 1. 按官方命令转换（原样照抄，不加参数）

```bash
conda run --no-capture-output -n robot-practice \
  python -m mani_skill.trajectory.replay_trajectory \
  --traj-path datasets/raw/maniskill_demos/PickCube-v1/motionplanning/trajectory.h5 \
  --use-first-env-state -c pd_ee_delta_pos -o rgb \
  --save-traj --num-envs 10 -b physx_cpu
```

产物 `.../motionplanning/trajectory.rgb.pd_ee_delta_pos.physx_cpu.h5`，约 12 分钟、约 78,000 帧。

**不加 `--allow-failure` 和 `--max-retry`**，官方脚本里没有，加了会改变哪些 episode 进数据集。
**不加 `--record-rewards`**，BC 不用奖励。

**转换只能在 CPU 做。** GPU 并行路径不支持控制模式转换，会报
`NotImplementedError: Replay with different control modes are not supported when replaying on GPU
parallelized environments`。也**不要试"CPU 转好再在 GPU 上不转模式重放一次"**——已实测不干净
（20 条里 9 条变短、1 条首成功=0、2 条被截到 ≤50、2 条从未成功），根因是 `replay_trajectory` 没有
`max_episode_steps` 参数而 motionplanning 的 episode 大多超过 50 步。

**转换前先清掉同名的试验产物**（20 条那次的输出与全量同名，会被静默覆盖）。2026-08-10 的已清。

### 5. 训练两臂

两臂**除 `--dataset.episodes` 外全部相同**。`steps` 必须提前定死且两臂一致——`factory.py` 第 41 行
`cfg.scheduler.build(optimizer, cfg.steps)`，`DiffuserSchedulerConfig` 是 `cosine`，**退火周期等于总
steps**，所以不同 `steps` 的 run 在同一步数上不可横比。M0 已在这上面误判过一次
（`train_main` 的 020000 是 0.585，`train_50k` 的 020000 只有 0.43）。

```bash
# 1000 条臂
conda run --no-capture-output -n robot-practice lerobot-train \
  --dataset.repo_id=local/maniskill_pickcube_mp_4d \
  --dataset.root=datasets/lerobot/maniskill/pickcube_mp_4d \
  --policy.type=diffusion --policy.device=cuda \
  --policy.n_obs_steps=2 --policy.horizon=16 --policy.n_action_steps=8 \
  --output_dir=outputs/maniskill/paper_aligned_4d/train_1000 \
  --job_name=paper4d_1000 --seed=1000 \
  --batch_size=32 --num_workers=4 \
  --steps=30000 --save_freq=2500 --log_freq=200 --eval_freq=0 --wandb.enable=false

# 100 条臂：只多 --dataset.episodes='[0,...,99]'，输出目录改 train_100，job_name 改 paper4d_100
```

`--batch_size` 是**每进程**的，8 卡下 32 × 8 = **256**，与官方一致（`lerobot_train.py` 第 336 行
`effective_bs = cfg.batch_size * num_processes`，日志会印 `Effective batch size: 32 x 8 = 256`）。
单卡跑就写 `--batch_size=256`。**开跑后必须去日志确认那一行印的是 256**——M0 那次我按 8 读成了
有效 batch 8，实际是 64，差点误判。

等效轮数：1000 条约 78,000 帧，30000 × 256 = 7.68M 样本 ≈ **98 轮**；100 条约 7,800 帧 ≈ **985 轮**。
论文两臂用同一个 `total_iters`，这里照做。**注意这比 M0 那次的 24.6 轮多 4 倍**，因为 M0 用的有效
batch 是 64。

`--eval_freq=0`：LeRobot 的在线评测走它自己的 env 层，本计划不走，评测在第 6、7 步自己做。

`--save_freq=2500` 给出 12 个 checkpoint。官方 `eval_freq=5000`（约 6 轮），我们存密一点、评全部，
取最大值时口径更保守（候选更多会抬高最大值，所以这一条对我们不利，是有意为之）。

### 6. 官方协议评测（主指标）

新写 `src/robot_practice/experiments/maniskill/eval_official_protocol.py`，**逐项照抄
`make_env.py` 与 `evaluate.py`**：

```python
env = gym.make("PickCube-v1", reconfiguration_freq=1, obs_mode="rgb",
               control_mode="pd_ee_delta_pos", max_episode_steps=100)
env = FlattenRGBDObservationWrapper(env)
env = FrameStack(env, num_stack=2)                 # obs_horizon
env = CPUGymWrapper(env, ignore_terminations=True, record_metrics=True)
env.action_space.seed(i); env.observation_space.seed(i)   # i in range(10)
eval_envs = gym.vector.AsyncVectorEnv([...10 个...], context="forkserver")
obs, info = eval_envs.reset()                      # 不传 seed
```

循环到 `eps_count >= 100`，每次 `truncated.any()` 时 `eps_count += num_envs`，并断言
`truncated.all() == truncated.any()`。指标从 `info["final_info"]["episode"]` 取。

**每个 checkpoint 都评一次，落盘全部，取 `success_once` 的最大值作 `official_best`。**
同时记 `success_at_end`、`fail_once`、`fail_at_end`，以及 `is_grasped`/`is_obj_placed`/
`is_robot_static` 三个原生阶段信号。

注意 `ignore_terminations=True` 的后果:**成功之后不停，跑满 100 步**。所以 `success_once` 与
`success_at_end` 会不一样(方块可能被碰掉)。M0 那套评测是成功即停,所以它的 `success_once` 与
`success_at_end` 恒等——两套口径不能直接比,这一条要写进结论。

由于评测不传 seed，**同一 checkpoint 重复评会得到不同数字**。为了让这个方差可见，对
`official_best` 那个 checkpoint 额外重复评 5 次，报均值与极差。

### 7. 留出集评测（本仓库口径，只跑一次）

只对第 6 步选出的 `official_best` checkpoint 跑，两臂各一次。

固定 seed，写进 `configs/experiments/maniskill/split_cpu.json`：

| 集合 | seeds | 数量 |
| --- | --- | ---: |
| `holdout` | 3000..3399 | 400 |

划分文件必须记下五条：`sim_backend: physx_cpu`、`num_envs: 1`、seed 以单元素列表逐条传
`reset(seed=[k])`、`max_episode_steps: 100`、`ignore_terminations: True`（与官方协议一致，
便于两个数对照）。

**CPU 划分不需要 M0 那套"首 seed 加行号"的约束**，因为每个 seed 独立决定状态（前置条件已实测），
所以按 seed 分片到多进程是安全的。

**与演示状态的隔离**：motionplanning 的 `reset_kwargs.seed` 是 0..1003，与 3000..3399 整数上不相交。
但那份数据生成于 commit `652ad9353c02`（branch `main`），本机是 3.0.1，**seed 能否复现录制状态是
未验证的假设**。所以先验：随机取 20 条，在 `physx_cpu` + `num_envs=1` 下 `reset(seed=[k])` 与源 h5
首帧 `env_states` 按容差 `1e-4` 比对。能复现则整数不相交即可；不能复现则退回指纹比对
（`[qpos, cube xyz, cube 四元数, goal xyz]` 最近邻，按分量分解报告）。结果写进
`leakage_report.json` 并写明走的哪条路。

**这个数不许拿去和论文比。**

## 判断标准

**执行前写死，看到数字之后不得修改。**

| 判据 | 阈值 | 不满足时怎么办 |
| --- | --- | --- |
| 转换存活率 | ≥ 95%（20 条试验是 100%） | 停止。查是否原样用了官方命令 |
| 动作越界比例 | **= 0%**（20 条试验是 0%） | 非零则查转换是否真在 CPU 上跑。这是本计划相对 M0 的核心改进，不能妥协 |
| 成功前帧占比 | ≥ 85%（20 条试验 89.2%） | 低于则转换后轨迹结构变了，停下来查 |
| 首次成功 p90 | ≤ 90 步（20 条试验 78） | 超过则 horizon 100 不够，按官方"约演示均长 2 倍"重定并记录 |
| 有效 batch | 日志印出 `Effective batch size: ... = 256` | 不是 256 就重跑，别事后换算 |
| 官方转换器可用性 | 已实测：产物能否被 `lerobot-train` 直接吃下去 | 不能则记录原因再自己写 |
| **1000 条臂的 `official_best`** | **≥ 0.90** | 见下面三档 |
| 100 条臂的 `official_best` | 无闸门，与论文的 0.76 并列记录 | 100 条方差大，不作判据 |
| `official_best` 的重复方差 | 已重复 5 次并报均值与极差 | 补测。不传 seed 的协议必须把方差摆出来 |
| 留出集 seed 隔离 | seed 能复现录制状态且整数不相交，**或** 指纹容差 `1e-4` 下无重复 | 停止，先修划分 |
| 留出集评测次数 | 每臂恰好 1 次 | 多跑就作废，重走第 6 步 |
| 随机基线 | 已实测并落盘 | 补测，不许假定是 0 |
| 特权 PPO 参照 | 已实测并落盘 | 补测 |
| 成功判定来源 | 只用 `info` 里的原生指标 | 改实现 |
| 测试与 ruff | 全绿 | 补测试 |

### 1000 条臂的三档结论

论文 Table III 报 1.00，是 `eval_freq=5000` 下约 6 轮评测里 `success_once` 的最大值。真实成功率在
0.95 附近时出现一次 1.00 很常见，**所以不要求 1.00**。

- **`official_best` ≥ 0.90**：管路对齐论文。M0 之前的 58.5% / 0.85 归因于数据与口径，不是实现错误。
  可以带着这个结论回去决定 7 维主线怎么改
- **0.75 – 0.90**：部分对齐。按影响排序查剩下的差异：模型实现（LeRobot 的 diffusion 对官方那份 DP，
  唯一已知不可对齐项）、`observation.state` 构成、图像预处理、`drop_n_last_frames` 之类 LeRobot
  特有的取样参数
- **< 0.75**：**管路里还有没定位的问题。** 停下来查，不要继续往 7 维主线推。这一档就是本计划存在的
  理由——它把"数据与口径"和"实现有 bug"这两种解释分开

## 风险与停止条件

- **控制模式转换只能在 CPU 做**，GPU 并行路径直接 `NotImplementedError`
- **不要用"CPU 转 + GPU 不转模式重放"的两段式**，已实测不干净（9/20 变短、1 条首成功=0、
  2 条截到 ≤50、2 条从未成功）
- **官方评测协议不传 seed，数字有 run-to-run 方差。** 不重复评就把单次结果当定数，是这个协议最容易
  出的错。判据里已要求重复 5 次
- **官方协议没有训练/评测状态隔离。** `official_best` 只能用来和论文比，不能当我们的正式成绩。
  这条要写进结论，别让后来读的人误用
- **`ignore_terminations=True` 与 M0 的成功即停是两套口径**，`success_once` 不可直接与 M0 的
  58.5% / 0.85 相减
- **CPU 与 GPU 的 seed→状态映射不同**（M0 3.1 第二条实测：seed=2000 在 CPU 是
  `[-0.089515 -0.094863]`，GPU 是 `[0.008543 0.050812]`）。`split_cpu.json` 与 `split.json` 是两套，
  混用会静默出错
- **`steps` 必须两臂一致且提前定死**，cosine 退火周期等于总 steps
- **有效 batch 要看日志确认。** M0 那次我把每进程 batch 8 读成了有效 batch 8，实际是 64
- **不要自己写成功谓词。** RF7 的旋转参考角用 0 弧度而非 `π/4`、Prompt Swap 在环境重置之后才评估
  把一整列清零成 0/10——两次都是自写判据出的事
- **不要把视觉学生与特权 PPO 的差值当成感知代价**，也不要把 PPO 叫上限
- **`--overwrite` 类操作要小心。** `train_b0.py:74` 的 `_clear_run_artifacts` 直接 `shutil.rmtree`
  整个 run 目录，B0 的产物已因此丢过一次。新入口对已存在的输出目录默认拒绝而不是删除
